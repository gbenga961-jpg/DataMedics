# Background Job Reliability

## Procedure

1. Read PRD §16 and the applicable project instructions before changing or reviewing queue or worker logic.

2. Treat PostgreSQL as the authoritative source for application job status and outcomes. Treat BullMQ/Redis as the delivery and execution mechanism.

3. Confirm that the persistent database job record exists before submitting the job to the queue.

4. Use the approved deterministic queue identifier:
   - Analysis: `analysis-{processingJobId}`
   - Cleaning: `cleaning-{cleaningRunId}`

5. Enforce idempotency using authoritative database state, unique constraints, request idempotency keys and deterministic output identifiers.

6. For a repeated cleaning request:
   - Return the existing run when the idempotency key and request fingerprint match.
   - Return a conflict response when the same key has a different fingerprint.
   - Do not create a duplicate logical run.

7. When a worker receives a job:
   - Load the authoritative database record.
   - Verify that the job is eligible to run.
   - Verify source-file availability and retention state.
   - Atomically claim the job.
   - Record the attempt, start time, heartbeat and lease.

8. Process the job without repeating work already durably completed.

9. Persist findings or output metadata before marking the application job completed.

10. On failure, record a safe error code and the appropriate retry or failure state.

11. Apply the approved retry policy:
    - Maximum three total attempts, including the initial attempt.
    - Initial backoff delays of 30 seconds and 60 seconds.
    - Retry temporary failures only where safe.
    - Do not retry permanent validation errors, unsupported files, limit violations, expired source files or invalid cleaning selections.

12. Reconcile persisted jobs that were not successfully submitted to or represented in BullMQ. Re-enqueue them using the same stable queue identifier.

13. Recover stale `PROCESSING` jobs only after checking whether an active worker still owns the BullMQ execution.

14. During recovery, respect attempt limits, prevent concurrent processing of the same logical job and never reset a completed job to queued.

15. Use deterministic object keys and safely reuse or replace stored objects after partial failures.

16. Record recovery history and safe error information.

17. Log job identifiers, job type, status, attempts, timestamps, duration, safe error code, worker identity and recovery history.

18. Never log raw CSV contents, passwords, authentication tokens, private storage keys or database credentials.

19. Verify the J05 acceptance tests in PRD §16.11.

## Completion checks

- Database state reflects the actual durable job outcome.
- Duplicate delivery does not create duplicate work or outputs.
- Retry and recovery limits are enforced.
- Completed jobs remain completed.
- Partial failures can be safely recovered.
- Logs contain no prohibited sensitive information.
