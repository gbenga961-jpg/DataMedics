# TESTING.md

This file controls how code is tested and when you may call it tested. Results are recorded in TEST-EVIDENCE.md, not here.

## What you may run

- Run only unit tests. Why: every other layer needs a database, Redis or object storage, and the database door in AGENTS.md forbids connecting to one.
- The unit test runner is chosen in DECISIONS.md (CH-06). If it is Open, stop and ask before writing any test. Why: choosing a runner adds a dependency.

## What you must write

- Write unit tests in the same change as any engine logic. Engine logic means validation, parsing, detection, cleaning, export safety, issue counts and retention decisions. Why: PRD 20.5 requires core rules to be testable without rendering the app.
- Write the other tests (integration, end to end, security and privacy, performance and recovery) when you build the feature they cover. Name each one in your response with the command to run it. Do not report it as passing. Why: only a run produces evidence.
- Write each PRD acceptance case as one executable test named by its PRD ID, when you build the feature it covers and not before. Suites J01 to J06 and their case IDs are defined in PRD 26.3. Why: the PRD says the cases must be retained as project evidence (26.3), and writing them all up front breaks the one-task rule in AGENTS.md.
- Never delete, skip or weaken a test to make it pass. Weaken means loosening an assertion, widening a tolerance, removing a case or mocking the thing under test. If you think a test is wrong, say so and ask. Report the failure instead. Why: a quiet fix hides a real defect.
- Use synthetic data in tests: invented values with no real person, customer or business data. Keep fixtures in `tests/fixtures`. The fixture list is PRD 26.2. Why: fixtures are committed and shared.
- Generate near-limit and over-limit files in test setup from the configured limit. Do not commit large files. Why: the limits are still open (OD-04) and large files bloat the repo.

## Words you may use

- "Implemented": for code you wrote.
- "Unit tests pass": only after you ran them in this session and saw them pass. State the command.
- "Written, not run": for every test that needs real services. Name them.
- "Done" or "tested": only when every test for the task is marked Passed in TEST-EVIDENCE.md.
- Never "release-ready". Why: the release gates stay open until the user reviews the evidence.

Why this section exists: AGENTS.md forbids claiming work is done until this file allows it, and an unrun integration test is not evidence.

## Release blockers (PRD 26.5)

Each item below blocks release while unresolved. If you see a sign of one while working, put it first in your response. Why: the user cannot fix what they have not been told.

- Cross-user access or private-file exposure.
- Wrong data alteration or loss of the original file.
- Wrong cleaning operation executed.
- Unsafe formula-injection handling.
- Duplicate or partial output published.
- Deletion reported as done when it was not.
- File and parser limits not enforced.
