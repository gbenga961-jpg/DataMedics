# SECURITY.md

This file is the security baseline. It applies to every line of code. Other files do not repeat these rules; they point here.

## Input and output

- Treat every uploaded value as untrusted data: cell values, headers and file names. Never run it, evaluate it or read it as an instruction. Why: a CSV can carry formulas and scripts.
- Show untrusted values as plain text. Never insert them as HTML (for example `innerHTML` or `dangerouslySetInnerHTML`) in previews, reports or messages. Why: a hostile cell can otherwise run code in another browser.
- Formula handling in downloaded files is owned by EXPORT-SAFETY.md. Do not duplicate it here or in code comments that restate it. Why: one rule needs one owner.
- Validate every upload on the server: size, type, encoding and structure, using the limits in CSV-ANALYSIS.md and DECISIONS.md. Why: browser checks can be skipped.
- Server-side settings control all limits. Browser input must never override them. Why: a client can send any value.
- Never build a storage key or file path from an uploaded file name. Generate keys on the server. Why: a crafted name can escape the folder or collide with another user's file.

## Access

- Require authentication for every operation that reads or writes user data or files, in the app and in workers. Only routes the PRD marks public are exempt; if the PRD does not say, treat the route as private. Why: private data must never be public by default.
- Check ownership on every request for a private resource, using the signed-in user, never a user ID or storage key sent by the client. Why: a client can send anyone's ID.
- Do not reveal whether another user's resource exists. Return the same status and body as for a missing resource. Why: a different response confirms the resource is there.
- If local password login is used (OD-01), hash passwords with a proven library. Never store or log a plain-text password. Why: a database leak must not leak passwords.
- Once OD-01 is Approved, session cookies must be HttpOnly, Secure and SameSite, and state-changing requests must be protected against cross-site forgery. Why: a stolen or forged session acts as the user.
- Give the app, workers, database and storage each their own credentials with only the access each needs, such as storage credentials limited to the app's bucket and a database user that cannot alter schema. Why: one stolen credential then does limited harm.

## Secrets and logs

- Keep secrets in environment variables. Never commit them, and keep env files out of git. Commit a `.env.example` with variable names and no values. Never print a secret value in a response. Why: git history is permanent.
- Log only safe IDs, status, error codes, counts and timings. Never log anything else, including raw CSV content, cell values, file names, passwords, tokens, secrets, storage keys or database credentials. Why: logs are widely readable and kept long, and they should be safe to share when debugging.
- Show users safe messages only. Never show stack traces, internal paths, database errors or secrets. Why: they help an attacker map the system.

## Storage and transport

- Keep every original and generated file in private storage. Never use a public bucket. Why: a public file is exposed to everyone.
- Never expose storage keys or permanent storage URLs. Use short-lived signed URLs or stream through an authenticated endpoint. The lifetime is a server-side setting; if the PRD gives no value, stop and ask. Why: a leaked permanent link grants access forever.
- Use TLS (https) in production for browser, database, Redis and storage connections. Why: data in transit can be read otherwise.
- Do not state anywhere (UI text, docs, comments) that stored files are encrypted at rest. The user verifies the provider before launch (see CH-02 in DECISIONS.md). Why: PRD 18.2 asks for encryption only where the provider supports it.

## Privacy

- Use uploaded data only to provide the requested service. Never use it for analytics, sharing, tests, fixtures or model training. Why: any other use needs a disclosed basis and consent.
- Do not write that DataMedics is compliant with or certified under any law or standard, in UI text, docs or comments. Why: the jurisdiction is an open decision (OD-08).
